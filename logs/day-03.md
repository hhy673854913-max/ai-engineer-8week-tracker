## 代码思考题回答

> 题目见课程文档的「代码思考」小节，答 2–3 题即可，写出你的判断和依据。

1.  本质是LLM没有记忆的问题，带来的问题就是成本，上线文每次都要带上导致token开销越来越大，其次就是延迟，处理时长也越来越高
滑窗（Sliding Window）
只保留最近 N 轮对话，更早的直接丢弃：
优点 ：实现最简单，token 数有上限 缺点 ：丢失早期上下文，用户问"我一开始说了什么"就答不上来
```python
def slide_window(messages, window_size=10):
    return messages[-window_size:]
```
摘要（Summary）
对话太长时，把早期的多轮对话压缩成一段摘要，替代原始历史：
优点 ：保留了关键信息，压缩比高 缺点 ：需要额外一次 LLM 调用来生成摘要（也有成本），且摘要可能丢失细节
```python
def summarize(messages, model, max_tokens=1000):
    return model.generate(messages, max_tokens=max_tokens)
```

缓存（Cache）
利用 API 供应商的 前缀缓存 机制（如 Anthropic 的 prompt caching、DeepSeek 的 context caching）：
两次请求的 前缀相同 时，服务端会缓存已计算的注意力结果，重复部分按折扣价计费甚至免费。
优点 ：对客户端完全透明，不用改逻辑 缺点 ：只有部分供应商支持，且缓存有时效性（通常几分钟到几小时）

在实际项目中，通常是 组合使用 ：滑窗控制上限 + 摘要保留关键信息 + 缓存降低成本。这个项目的`llm_client.py` 目前是每次完整传 messages，还没有实现这些优化——如果需要，可以在 Agent 层加上滑窗和摘要逻辑

2. 429 为服务端限流，服务端告诉要来得慢一点处理不过来，所以延迟请求可以ok，但是如果不加抖动的话，再次同步请求，大概率再次触发429错误

3. 如果概率低其实不需要处理，如果概率比较高，看是否是超时时间设置过小导致的长请求被当做超时处理。
