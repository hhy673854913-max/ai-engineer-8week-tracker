## day-01 · 环境管理与 JS→Python 语法迁移

- **P2 · 1. 为什么 Python 是 AI 生态的第一公民** ｜ 问题：整节只用「生态惯性」解释 Python 的地位，落点是"读得懂、改得动、封得住"这种抽象目标。没有一句说明这 8 周里哪一段必须落到 Python（向量库客户端、Agent 编排、评估、服务化），也没提 M1/M2/M3 的交付物本身就是 Python 服务，读者读完仍不知道"我哪一部分工作要用 Python"。｜ 建议补写：具体到岗位：RAG 的向量库与 embedding 客户端、Agent 编排（LangGraph）、评估（RAGAS）、服务化（FastAPI）在 Python 侧都是一等公民，M1/M2/M3 的交付物也全是 Python 服务。你不是要从头学一门语言，而是要把 AI 能力包成 Python 服务、再接回你最强的 React 界面。

- **P1 · 3. 语法对照表（照着敲一遍）** ｜ 问题：小节标题就写着"照着敲一遍"，整张表只做 JS→Python 的写法映射，没有一处说明这些写法会出现在什么代码里。而表里的 `d["key"]`、`a.get("b")`、`o.items()` 恰好是解析模型 `tool_calls` 参数、处理返回值缺字段时要写的第一行代码——练完只会抄表，不会把它和 Agent 代码联系起来。｜ 建议补写：这张表至少三行在 Agent 代码里天天出现：模型返回的 `tool_calls[0].function.arguments` 是 JSON 字符串，`json.loads` 之后就是 `d["name"]` / `d.get("arguments", "{}")`；`messages` 是 `list[dict]`，追加一轮对话就是 `messages.append({"role": "user", ...})`。敲完表顺手写个 `parse_tool_args(raw: str) -> dict`，这是第 5 周工具调用的第一块砖。

- **P1 · 4. 五个会咬人的差异（今天就记住）** ｜ 问题：五个差异都只给语言层玩具例子（`def f(items=[])`、`if data:`），没有交代它们在 Agent 代码里的后果。可变默认参数放在工具函数上就是跨请求状态泄漏，`if not docs:` 放在检索链里会把"检索到 0 条"和"检索没跑"混成同一条降级路径——这两类都是会上事故复盘的 bug，文中一个字没提。｜ 建议补写：这两个坑在 Agent 里是事故级的：工具函数写 `def search(q, filters={})`，同一进程里所有请求共享那个 dict，A 用户的过滤条件会漏进 B 用户的检索；检索后写 `if not docs:`，会把"确实没命中"和"检索抛错被吞"压成同一条降级路径，线上只能靠日志猜。

## day-02 · 类型注解、Pydantic 与 CLI 工具

- **P0 · 2. `dataclass` vs `Pydantic`：一条判断线** ｜ 问题：全节只有半句"Pydantic：边界上的数据……会做类型转换 + 校验 + 报错信息"，既没说 Pydantic 是什么（`BaseModel` 是什么、实例化时到底发生了什么）、能做什么（校验 / 序列化 / 生成 JSON Schema），也没说它在 Agent 工程里具体顶哪几个位置。读者记住了"数据从外面进来就用 Pydantic"这句口诀，却不知道在 M1/M2/M3 里该把它写在哪一行。｜ 建议补写：**Pydantic 是 Python 的数据校验库**：你把字段声明成 `class X(BaseModel)`，实例化那一刻它就把输入逐个校验、必要时转换（`"3"` → `3`），不合法直接抛 `ValidationError` 并指到具体字段；同一份声明还能导出 JSON Schema、直接序列化成 JSON（`model_dump_json`）。它的位置在**系统边界**：外面进来的数据不可信，进门先过它。在 Agent 工程里它有三个躲不开的落点——① 模型返回的 JSON（Day 05 的结构化输出、Day 22 的工具参数），不校验就带着脏字段往下跑；② 工具的函数 schema，Function Calling 要求你提供 JSON Schema，`BaseModel.model_json_schema()` 直接生成；③ FastAPI 的请求体（Day 34），422 报错和 OpenAPI 文档都是它给的。所以判断线不是"dataclass 旧、Pydantic 新"，而是：**数据在自己进程内部流转用 dataclass，跨过信任边界（模型、用户、网络）就用 Pydantic**。

- **P1 · 3. 异常处理：别写 `except Exception: pass`** ｜ 问题：三条纪律写得清楚，但落点只有"CLI 层统一翻译成退出码"和"面试常问"。对 Agent 工程师，异常分层真正决定的是"哪些失败该让模型看见并自己换策略、哪些必须立刻终止"，本节没有一个字提到 LLM 调用失败、工具超时、检索为空这些场景。｜ 建议补写：这套分层第 5 周会原样变成工具的错误契约：`ToolError`（参数不对、结果为空）要作为 tool 消息回传给模型，让它换参数或换工具；`ConfigError` 和权限错误要直接终止并告警，因为重试一百次也不会成功。分层错了，Agent 会对一个必败的工具死循环，把配额和延迟一起烧光。

- **P2 · 4. `logging` 而不是 `print`** ｜ 问题：本节把 logging 定位成"print 的替代"，唯一的岗位连接是一句"AI 应用里日志就是你的可观测性雏形（Day 33 展开）"。没有说 Agent 排障时一行日志里必须有哪些字段，读者到 Week 7 做链路追踪时不会意识到那套字段是今天该埋的。｜ 建议补写：在 Agent 里，一行日志要能串成一条 trace：`trace_id`（一次用户请求）、`span`（每次 LLM 调用/每次工具调用）、`model`、`prompt_tokens`、`completion_tokens`、`tool`、`latency_ms`。出问题时你不是翻 print，而是按 trace_id 把一次提问的每一步捞出来——Day 33 只是把这些字段换成结构化后端，字段本身今天就要设计对。

- **P2 · 任务 2 · argparse 子命令（40 min）** ｜ 问题：子命令练习的落点只有一句"dry-run 默认开启是运维级习惯"，没有说明这套设计跟 Agent 的关系。而工具的参数 schema、危险操作默认干跑，恰恰是第 5 周注册工具时的核心问题。｜ 建议补写：把子命令想成工具：`scan` / `rename` 就是两个工具名，`--dir` / `--prefix` 就是它们的 `parameters` JSON Schema。今天的 `--apply` 第 5 周会变成工具参数 `dry_run`（默认 true）——模型先预演、人确认后再执行，这是防止模型一次幻觉就真删数据的最低成本手段。

## day-04 · 流式输出与采样参数

- **P1 · 2. SSE 长什么样** ｜ 问题：全节只描述报文形态（`Content-Type: text/event-stream`、`data:` 行、`[DONE]`），"SSE" 三个字母从没展开，也没说它是什么协议、解决什么问题、客户端怎么消费。读者是前端出身，手里本来就有 `EventSource` / `fetch` + `ReadableStream`，文中没把两侧接起来，也没回答"为什么不直接用 WebSocket"。｜ 建议补写：SSE（Server-Sent Events）是浏览器原生支持的服务端单向推送协议：一条 HTTP 长连接上服务端持续写 `data:` 行，客户端用 `EventSource` 或 `fetch` + `ReadableStream` 逐条读；它解决的是普通 HTTP「一问一答」里服务端没法边算边推的问题，单向推送用它就够，不必付 WebSocket 的双向与心跳成本。这半边你其实已经会——前端那侧的消费代码就是你现成的资产。

- **P2 · 1. 为什么流式是"体验"而不只是"性能"** ｜ 问题：整节把流式论证成"感知等待从 8 秒降到 0.8 秒"的体验问题，对要写服务端的 Agent 工程师还有两个更硬的动机没提：长生成会撞网关/反代的空闲超时；Agent 的检索、工具调用等中间步骤只能靠流式事件透出去。｜ 建议补写：对 Agent 工程师还有两个更硬的理由：一是长输出的总耗时经常超过网关/负载均衡 60s 的空闲超时，流式让连接一直有数据、不被掐断；二是"正在检索/正在调工具/正在重写"这些中间状态只能靠流式事件推给前端，否则用户看到的是几十秒无反馈的白屏。

## day-05 · 结构化输出与运营文案生成器

- **P1 · 1. 为什么"结构化"是分水岭** ｜ 问题：本节把下游写成"下游代码要解析、要入库、要校验、要展示"，但全天的落地场景被钉在"资深游戏运营文案"，一次都没提 M1 智能简报，也一次都没提工具调用。"用你最熟的运营场景"这个前提对目标读者（5 年前端）本身就不成立；而结构化输出在 Agent 岗位最硬的用途——`tool_calls` 的 arguments 就是一份必须过 schema 的 JSON——全文缺席。｜ 建议补写：在 Agent 里，结构化输出的头号用途不是文案而是工具调用：`tool_calls[0].function.arguments` 就是一段必须过 schema 的 JSON，参数不合法工具就直接执行失败——Day 22 注册工具时，工具的入参模型就是你今天写的这个 Pydantic 类。把 `CopyVariant` 换成下周 M1 简报的 `BriefItem`（title/summary/category/credibility），这套"校验→回传错误→重试"可以原样跑 100 条资讯抽取。

- **P2 · 5. 提示词模板（可直接抄）** ｜ 问题："这样模板可缓存（部分厂商支持 prompt caching）"——prompt caching 首次出现就被当作已知概念，用来支撑"变量放末尾"的建议，但没说它缓存的是什么、省在哪。读者记不住这条设计理由，更不会想到把它用在 Agent 那种几千 token 的 system prompt + 工具定义上。｜ 建议补写：prompt caching 指把固定前缀的 token 计算结果缓存住，命中后不再重复计算、通常也不再重复计费，所以"固定指令在前、变量在后"不是排版偏好，而是让每次请求的前缀完全一致以打中缓存。Agent 的 system prompt + 工具定义动辄几千 token、每次请求都重发，这一条能同时压低首字延迟和输入成本。
