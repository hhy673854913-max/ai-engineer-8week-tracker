## day-26 · MCP 协议精读与官方 SDK 跑通

- **P1 · 3. 传输方式** ｜ 问题：本节列完三行传输表就以"本地开发 99% 用 stdio"收尾，既没说明你在什么情况下需要自己选传输，也没落到本周的实际链路——你的 Agent 是用 stdio 把 M1/M2 两个 Server 当子进程拉起来的，而换成远程之后多出来的那层权限责任完全没提，读者拿到"远程 HTTP"这个选项也不知道还要补什么。｜ 建议补写：在 M3 里你会用 stdio 同时拉起 M1、M2 两个 Server——它们就是 Agent 的子进程，跟着 Agent 一起启停，这也是为什么 Day 27 的日志不能写 stdout。等这套东西要给别的团队远程调用，才换成 Streamable HTTP，而此时"谁能调、能调哪几个工具"必须你自己在 Server 里判，协议层不会替你挡。

- **P0 · 5. 协议消息长什么样（JSON-RPC）** ｜ 问题：JSON-RPC 2.0 在架构图（`JSON-RPC 2.0`）、本节的报文示例、Day 28 的错误分层（"协议层……返回 JSON-RPC error"）里反复出现，但全文没有一句话说明它是什么；`{"jsonrpc":"2.0","id":1,"method":"initialize",...}` 直接摆出来，读者只能靠猜 `id` / `result` / `error` 的关系，更不知道为什么既然要用 FastMCP 还要读这种原始报文。｜ 建议补写：JSON-RPC 2.0 就是"用 JSON 传远程调用"的约定：请求带 `jsonrpc` / `id` / `method` / `params`，服务端用同一个 `id` 回 `result` 或 `error`，MCP 的每一条消息都是这个壳。平时用 SDK 你看不到它，但握手失败、工具名对不上、客户端收不到响应时，抓的就是这几行——面试问"MCP 底层怎么通信"答的就是这个。

- **P1 · 任务 1 · 安装与最小 Server（60 min）** ｜ 问题：上午刚讲完手写报文和生命周期，任务 1 直接跳到 `from mcp.server.fastmcp import FastMCP` 加 `@mcp.tool()`，没有一句交代 FastMCP 是什么、和上面那些 JSON-RPC 报文是什么关系，读者会觉得上午学的协议白学了，也不知道自己写的是"标准做法"还是"简化封装"。｜ 建议补写：FastMCP 是官方 SDK 上的一层封装，定位类似 FastAPI：你写普通函数挂 `@mcp.tool()`，它负责生成 `tools/list` 要的 schema、接住 `tools/call`、把返回值包成 JSON-RPC 响应——上午那些报文它替你发了。真实项目里绝大多数 Server 都这么写，只有调不通时才回头抓报文。

## day-28 · MCP 进阶：资源、提示模板与调试体系

- **P1 · 5. 性能与并发** ｜ 问题："高频工具加进程内缓存（TTL 60s）"之下紧跟的示例却是 `@lru_cache(maxsize=256)`——`lru_cache` 只按容量淘汰、没有过期时间，照抄得不到 60 秒 TTL；同时本节没有一句解释 `lru_cache` 是什么，读者会误以为它就是"TTL 缓存"，上线后数据脏了也查不出原因。｜ 建议补写：`lru_cache` 是 functools 里的装饰器，按入参缓存返回值、超出 `maxsize` 就淘汰最久未用的，它没有过期时间；要 60 秒 TTL 得用 `cachetools.TTLCache`，或者自己存 `(值, 取到的时刻)`，读的时候超过 60 秒就重取。知识库这种一天改几次的数据，用无过期的缓存会让你的 Agent 一直答旧文档，面试里被追问"缓存怎么失效"时这就是答案。

- **P1 · 1. 三种编排** ｜ 问题：标题和今日目标都在讲"多智能体"，本节却直接从三行编排表开始，全文没有一句定义什么算多智能体——尤其是它和 Day 24 那个"单 Agent 里挂多个 LangGraph 节点"的界线，导致 §2"能用单 Agent + 好工具解决的，不要上多智能体"这条判据读者无法对号入座。｜ 建议补写：先划一条线：同一个 Agent 里加节点、共用一份上下文和一份 system prompt，那还是单 Agent；只有当每个角色有独立的 system prompt、独立的输入输出契约、能被单独跑和单独验收时，才算多智能体。面试问"你们到底是几个 agent"时，答的就是这条线，而不是数节点个数。
