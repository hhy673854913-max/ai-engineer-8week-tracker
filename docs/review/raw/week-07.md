# week-07 审校结果

## 周总评

本周是全课程里离目标岗位最近的一周：评估、trace、SSE、降本四件事都是 AI 应用 / Agent 岗面试的必答题，任务也都压在 M2 的真代码上，这是优点。问题在于这一周的通病是**把工具当成读者已知**——RAGAS（Day 32 全天的主角）、Langfuse（Day 33 唯一的外部平台）、LLM-as-judge（贯穿 Day 31/32/35 的"judge 模型"）、FastAPI 的 `Depends`，都是先出现在标题、对比表或代码里，全周没有一处给出"它是什么、替你解决了什么"的一句话，读者能照抄跑通，却答不出面试官那句"你为什么用它"。第二个共性是**落点全压在 M2 的单轮问答上，Agent 侧缺席**：本周的 trace 和评估都只针对"一次提问"，没有一处点明 M3 那种多步工具调用的轨迹该怎么埋点、怎么判断"这一步该不该调这个工具"、一次 Agent 运行的成本该怎么归属，而这恰恰是 Agent 工程师岗位的核心追问；建议在 Day 32、Day 33 各补一句"同样的方法套到 M3 的 Agent 轨迹上是什么样"，让这一周练出的能力可迁移，而不只是 M2 的收尾。

## day-31 · 评估方法论与评估集构建

- **P0 · 5. LLM-as-judge 的边界** ｜ 问题：这一节标题就叫 LLM-as-judge，正文却直接从"能用：批量粗筛、对比两版输出、回归测试。不能全信：细微事实错误、领域黑话、需要外部知识的判断"开始，全文没有一句说明它是什么、judge 靠什么机制打分；§2 的方法栏也只写了"人工 / LLM-as-judge / RAGAS"四个字。从 Day 32 起"结果受 judge 模型影响很大""用便宜模型当 judge""judge：deepseek-chat"反复出现，读者始终分不清自己在看模型自评、另一个模型的打分，还是某个平台的功能，也就无法理解代码思考 4 里"与人工一致率 65%"到底在算什么。｜ 建议补写：LLM-as-judge 就是让另一个 LLM 当打分员：把问题、检索到的资料、待评答案和你这份评分细则一起塞给它，要求它先写理由、再按 1–3 分输出 JSON，用它的判断替代人工逐条看完 50 条样本。Day 32 里 RAGAS 的每个指标底层都是一次这样的调用，"judge 模型"就是被指定当打分员的那个模型——所以它必须固定版本，否则同一份评估集今天 0.86、明天 0.79，你的改进和噪声就分不开了。

## day-32 · RAGAS 自动化评估

- **P0 · 1. RAGAS 的四个核心指标** ｜ 问题：标题和今日目标都以"用 RAGAS 跑通自动化评估"为前提，但正文第一句就进四指标表，全节没有一句"RAGAS 是什么"；§2 的"RAGAS 不是'公式计算'，它内部大量调用 LLM 做判断"是唯一接近定义的一句，读者很可能把它理解成这四个指标的合称或某个在线服务，直到 §3 看到装包、`Dataset` + `evaluate` 才反应过来它是个库，也不清楚它和 Day 31 自己建的 `eval_set.jsonl` 是什么关系、要不要重新准备一批数据。｜ 建议补写：RAGAS 是一个开源的 Python 评估库，本身不做检索也不做生成，只负责打分：你把 Day 31 那批样本（question / answer / contexts / reference_answer）喂进去，它用 LLM 当裁判把四个指标各算成一个 0–1 的分数，输出一张能直接贴进 README 的表。所以它不是"另一套评估数据"——你昨天那 50 条就是它的输入，`reference_answer` 对应它要的 `ground_truth`，负样本则留在 RAGAS 之外单独算拒答率。

## day-33 · 可观测性：链路追踪与提示词版本管理

- **P1 · 3. Langfuse / LangSmith 怎么选** ｜ 问题：小节标题第一次出现这两个平台，正文立刻给出"部署 / 价格 / 强项 / 接入"四行对比，没有一句说清它们是干什么的；结尾"国内团队常选自托管 Langfuse（数据不出内网）。没有条件就先用日志自己实现"又把决定权丢回给读者。刚手写完 `Trace` 类的人无法判断这个平台比自己的 JSON 日志多解决了什么，"接入：SDK 装饰器"这一行也看不出和任务 2 的 `@observe()` 是同一件事，代码思考 5 的"多解决了什么"因此在没有铺垫的情况下被问了出来。｜ 建议补写：Langfuse 是一个开源的 LLM 应用追踪平台：你在 retrieve / rerank / generate 外面包一层装饰器，它自动把每次调用的输入输出、延迟、token 攒成一棵可点开的树，还能按 prompt 版本、按评估分数做对比——相当于把你今天手写的 `trace.to_dict()` 从一行 JSON 变成"能搜索、能按 trace_id 翻出那次到底检索到了什么、能给同事发链接"的界面。LangSmith 是同一类东西，差别只在和 LangChain 的集成更紧；两者都不改变今天学的心智模型，只是把落盘和查询托管掉。

## day-34 · FastAPI 服务化：路由、SSE 与错误处理

- **P1 · 2. 依赖注入：把重资源放 lifespan** ｜ 问题：今日目标把"依赖注入"列为本节要学的东西，但这一节只讲了"不要在路由里 `QAService()`：每次请求都重新加载索引，1 秒起步，还会打爆内存"，`Depends` 第一次出现是下午任务 1 的 `service: QAService = Depends(get_service)`，既没说它是干什么的，也没交代为什么不能像 Node 那样直接模块级单例导出一个 service。对 React/Node 背景的人来说，"框架在请求时替你调用函数并注入参数"是一套全新约定，不是查一下 API 就能补上的，后面任务 2 里 `Depends(get_service)` 和 `request: Request` 混写也会读得似是而非。｜ 建议补写：`Depends` 是 FastAPI 的依赖注入：你在函数签名里声明"这个接口需要一个 QAService"，FastAPI 在每次请求进来时调用 `get_service`，把 lifespan 里建好的那个实例作为参数传进来，路由函数里就不用自己 import 全局对象。好处有两个：取 service 的逻辑只有一处，以后要按请求注入 db session、当前用户、trace_id 都是同一套写法；测试时用 `app.dependency_overrides[get_service]` 换成假 service，不加载真索引就能跑接口测试——面试被问"你们服务怎么做单测"时，答的就是这一句。

## day-35 · Docker 化、部署与降本实验

- **P1 · 1. 镜像的四个原则** ｜ 问题：原则表把"用 `python:3.12-slim`，多阶段构建"列成"小 / 攻击面小"的做法，但全文没有一句解释多阶段构建是什么；任务 1 给的 Dockerfile 又只有一个阶段——`FROM python:3.12-slim AS base` 之后直接 `CMD`，`AS base` 再没被引用过。读者会以为给 FROM 起个名字就叫多阶段，照抄下来既没减体积，也不知道哪天真的需要第二个阶段，而"镜像为什么这么大"正是上线后第一个被问到的问题。｜ 建议补写：多阶段构建是把"装依赖 / 编译"和"运行时"拆成两个 FROM：第一个阶段（builder）里装 gcc 和需要编译的包，第二个阶段只 `COPY --from=builder /usr/local/lib/python3.12/site-packages` 加上你的代码，最终镜像里没有编译器、也没有 apt 缓存，体积和攻击面一起降下来。任务 1 这份依赖全是纯 Python 包，单阶段就够，所以只写了一个 `AS base`；等你把 `faiss-cpu`、`onnxruntime` 装进镜像时再加第二个阶段。
