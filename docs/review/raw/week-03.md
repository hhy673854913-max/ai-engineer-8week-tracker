# week-03 审校结果

## 周总评

week-03 把 RAG 的每个零件讲得比多数教程细，但视角是"检索流水线"而不是"Agent 工程师"：Chroma、BM25、交叉编码器、LangChain 多处只报名字就开用；加载器与查询改写讲了却不落地；"检索在 Agent 里是被模型按需调用的工具"这个位置全周（无一次 M3 / Agent / 工具调用字样）没有出现，M1/M2 落点也只在 day-14 出现两次。补齐这些落点后，这一周才能直接拿去讲面试。

## day-11 · 嵌入向量与语义相似度

- **P2 · 任务 1 · 纯手写相似度（40 min）** ｜ 问题：给手写版唯一的理由是"不 import numpy 也能跑通（用于理解）"，没交代这个能力在岗位里落在哪：面试白板写余弦、线上排查"这条明显相关的文档召回分只有 0.61"时手算复核、无 numpy 依赖的小库兜底。读者（5 年前端）会合理地问：numpy 三行就写完，为什么还要手写？｜ 建议补写：手写这一版不是为了理解而理解：面试会让你白板写余弦并解释"为什么归一化后点积就是余弦"；线上排查"这条明明相关的文档召回分只有 0.61"时，你也得能手算一遍，确认是向量、归一化还是阈值的问题。两个版本都留在 `similarity.py` 里，numpy 版给后面检索用，纯 Python 版留给面试复盘。

- **P2 · 任务 2 · 调用真实 embedding API（50 min）** ｜ 问题："`dimensions` 参数不是所有厂商都支持""批量接口一次最多 10–25 条"两条都停在 API 脚注层面，没有说它会怎样塑造 M2 的入库工程：上千个块分批、429 重试、断点续传、重复嵌入=重复付费。｜ 建议补写：这条批量上限直接决定 M2 入库脚本长什么样：要把上千个块按 10–25 条切片、失败重试、记录已完成的 batch，否则中途一次 429 就得从头再嵌一遍（也就重复付一遍钱）。今天先在 `embed()` 外套一层 `embed_batched(texts, size=16)`，M2 建索引时原样复用。

## day-12 · 文档加载与分块策略

- **P1 · 5. 从文档到块：加载器** ｜ 问题：`| PDF | pypdf / pdfplumber |` 这类"工具 + 坑"清单没有任何一句说明它在岗位里的分量：企业知识库七成以上是 PDF/Word/扫描件，解析错一行，后面的分块、嵌入、生成全跟着错，而这一步常占 RAG 项目一半工期。而且这节讲完就断——Day 13 的 `ingest()` 只 `rglob("*.md")`，加载器在整周代码里没有一个落点。｜ 建议补写：这一节是你和真实数据第一次打照面：企业知识库七成以上是 PDF/Word/扫描件，解析错一行，后面的分块、嵌入、生成全跟着错——M2 答得不准，一半原因在这里而不在模型。下午任务 2 请至少塞 5 篇 PDF 进 `data/kb`（`pdfplumber` 抽文本、抽不出字的页记进 `failed.txt`），先把"解析失败率"这个数字量出来，Day 13 的 `docs_dir.rglob("*.md")` 也顺手改成同时扫 PDF。

- **P2 · 2. 三种策略** ｜ 问题："这是 LangChain `RecursiveCharacterTextSplitter` 的思路"——LangChain 在本周首次出现，没有一句说明它是什么，也没说明本课程为什么坚持手写而不直接调用它。读者下次在 JD 和面试里碰到 LangChain 时，接不上这条线。｜ 建议补写：LangChain 是 Python 里最常用的 LLM 应用开发框架，`RecursiveCharacterTextSplitter` 是它的默认分块器——你之后多半会在公司项目里用到它，面试也一定会问"为什么不直接用 LangChain 的分块器"。手写一遍的价值在于你才知道每个分隔符在什么情况下失效，用框架时才调得动参数、出了问题才定位得到。

## day-13 · 向量库：存储、检索与增量更新

- **P1 · 4. Chroma 的基本用法** ｜ 问题：本节从"用 Chroma 完成增删改查"直接跳到 `chromadb.PersistentClient(path="./chroma_db")`，全篇没有一句说 Chroma 是什么、以什么形态运行。对有 Node 工程背景、默认"数据库/向量库 = 要 docker 部署并对接连接串的服务"的读者，`PersistentClient(path=...)` 会直接造成困惑：数据在哪、能不能多进程共享、上线怎么办。｜ 建议补写：Chroma 是一个 pip 装完就在进程内跑的嵌入式向量库：不用起服务、不用 docker，`PersistentClient(path="./chroma_db")` 把数据落在本地目录（这个目录就是你的数据库，删了就得重新入库），适合原型和单机演示；生产上团队更常见的是 pgvector（已有 Postgres 加个扩展就行）、Qdrant、Milvus，面试问"向量库怎么选"时你要能说出这三者的差别。今天用 Chroma 只是让你把注意力放在检索逻辑上，M2 之后换实现只改 `store.py` 这一层。

- **P2 · 任务 3 · 对照实验：语义 vs 关键词（40 min）** ｜ 问题："B 组：关键词匹配（`text.lower().count(query)` 或简单 BM25）"——BM25 在这里第一次出现，却要到 Day 15 才讲，"或"字把选择权直接丢给读者，此刻读者不知道该实现哪个、两者差别在哪。｜ 建议补写：今天的关键词基线就用最笨的 `text.lower().count()`：它只要跑出对照组数字、证明"向量在口语化问题上更强"就够了。BM25 明天手写，等你在 Day 15 看到它在 `SPRING2026` 这类专名上比 count 强一个档，就明白混合检索为什么值得维护两套索引。

## day-14 · 完整 RAG 链路与引用溯源

- **P1 · 1. RAG 完整链路（七步）** ｜ 问题：图里画了七步并强调 RW/F/M/P 四步，但下午的 `MiniRAG` 只实现了 R/E/F/C/G/P，查询改写与相邻块合并没有任何代码、也没说明今天故意不做；读者照着敲会以为漏写了。更关键的是全周都没交代这条链路的位置——在 Agent 应用里它是一个被模型按需调用的检索工具，而不是固定执行的流水线。｜ 建议补写：补一句位置说明：在 M3 的 Agent 里，这条链路不是固定执行的流水线，而是被包装成一个 `search_kb(query)` 工具交给模型，由它决定调不调、调几次、要不要改写后重试——本周你负责把工具内部做准（召回、引用、拒答），工具外面的事件循环留到 M3。另外今天先实现 R/F/C/G/P 五步就够：RW 的三种做法在 Day 15 §5，M（相邻块合并）等你有了真实评测数据再加，别在第一版就堆满。

- **P2 · 2. 上下文组装：不是简单拼接** ｜ 问题："总量控制：top-k × 块长 ≤ 模型上下文的安全水位"——"安全水位"是多少、超了先砍哪一块、怎么估算 token，全都没说。这是 Agent 工程师每天在调的预算（直接对应成本和延迟），也是 M2 上线时最容易踩的一次性故障。｜ 建议补写："安全水位"给个可执行数：中文按 1 字 ≈ 1 token 粗估，给资料的预算压在 6k–8k token，另留 2k 给输出；超预算时按 score 从低到高整块丢弃，不要截半块——被截断的块最容易让模型顺着半句话编。这个预算写进 `MiniRAG` 的配置（`max_context_tokens`），换模型、调 top_k 时先看它。

## day-15 · 混合检索、查询改写与重排序

- **P1 · 2. BM25 公式（理解即可，不背）** ｜ 问题：小节标题下一行就是公式，只解释了 tf/IDF/k1/b 四个符号——从未有一句话说 BM25 本身是什么（搜索引擎沿用了二十多年的关键词相关度打分函数，Lucene/Elasticsearch 的默认排序）、为什么它叫 25、以及"理解即可"要理解到什么程度；也没交代为什么 Agent 项目里要手写它而不是直接调 ES。｜ 建议补写：BM25 是搜索引擎用了二十多年的关键词相关度打分函数，Elasticsearch / Lucene 的默认排序就是它（名字里的 25 是作者当年的编号）。手写一遍的理由很实际：调混合检索时你得凭手感判断 k1/b 往哪调，面试也常问"BM25 和向量检索各强在哪"；生产里你多半直接调 ES 或向量库自带的 sparse 检索，公式不用背，但 IDF 在压什么、长度归一化在补什么必须能讲出来。

- **P1 · 4. 重排（Rerank）：用贵的模型看少数候选** ｜ 问题："交叉编码器｜BGE-Reranker｜中｜好"——"交叉编码器"是整个重排方案的核心，但从未解释它是什么，也没和召回阶段用的双塔 embedding 做对比：为什么它更准、为什么只能用在少数候选上。读者只能记住"BGE-Reranker 好用"，讲不出"召回 50 → 重排 20 → 取 5"这条数字链的由来。｜ 建议补写：补一句原理：召回用的 embedding 是双塔——query 和文档各自独立编码，文档向量能提前建索引；交叉编码器把 query 和文档拼成一对送进模型打分，能看见两者的交互，所以更准，但每条候选都要现算一次前向。这就是"召回 50 条、重排 20 条、给 LLM 5 条"的由来，也是面试问"为什么需要 rerank、延迟怎么控"时你要答的东西。

- **P2 · 5. 查询改写（Query Rewriting）** ｜ 问题：整节只有三张例子表和三种做法，结尾停在"代价都是额外一次 LLM 调用。先用规则，再考虑 LLM"——没有任何代码，下午四个任务也没覆盖改写，验收标准里也没有它。读者读完不知道这段加在 `MiniRAG` 的哪一层。｜ 建议补写：落点别停在表格：在 `MiniRAG.answer()` 第一行加 `queries = self.rewrite(question)`（规则版：把"这个/它"替换成上一轮对话里的实体），各自 `retrieve` 后用今天 §3 的 RRF 合并去重，再进 `build_context`——这才是"这个能退吗"能召回退款规定的地方。做完把改写前后的 hit-rate@5 记一笔，你就有数据回答面试官"查询改写值不值一次额外 LLM 调用"。
