# 提示词模式库

> 这不是收藏夹，是**你自己会反复用**的模板。每个模式都必须有：适用场景、模板、反例、实测效果。
> 见到新技巧时先问："它属于哪个模式？我什么时候会用？" 答不上来就别收藏。

## 1. 角色-任务-格式

- **适用**：几乎所有任务的起点。
- **模板**：

```text
你是{角色}，读者是{受众}。
请{任务}，输出{格式}，不超过{长度}。
```

- **反例**："帮我写个文案"。
- **要点**：角色不是装饰，它决定用词与详略；受众决定信息密度。

## 2. 分隔符隔离

- **适用**：任何包含用户输入的场景（必用）。
- **模板**：

```text
请只依据 <data> 中的内容回答，不要使用外部知识。
<data>
{input}
</data>
```

- **反例**：把用户输入直接拼在指令后面，模型会把它当指令执行。
- **要点**：同时提升效果与抗注入能力；分隔符要成对且唯一。

## 3. 结构化输出

- **适用**：下游代码要消费结果时。
- **模板**：

```text
只输出 JSON，不要 markdown 代码块，不要解释。
字段：{"field": "类型，约束"}
```

- **反例**：只写"给我 JSON"，然后在代码里 `json.loads` 整段输出。
- **要点**：配合 `response_format={"type":"json_object"}` + Pydantic 校验 + 修复重试。

## 4. 先分析后结论

- **适用**：判断类、评分类、易出错的复杂任务。
- **模板**：

```text
先在 analysis 字段写 2 句推理（必须引用原文），再填 result 字段。
JSON：{"analysis": "", "result": ""}
```

- **反例**：让模型"先解释再输出 JSON"，结果解释混进 JSON 导致解析失败。
- **要点**：把思考过程做成**字段**，可校验、可丢弃、可审计。

## 5. 少样本（Few-shot）

- **适用**：格式复杂、风格特殊、边界多的任务。
- **模板**：2–3 个与目标输出**同构**的示例，其中至少一个"信息不足 → null"。
- **反例**：示例比目标输出更详细，导致模型越来越啰嗦。
- **要点**：示例顺序有近因效应，最想强调的放最后。

## 6. 分步拆解

- **适用**：一次要求太多、模型顾此失彼时。
- **模板**：

```text
按顺序完成：
1. 提取所有时间与数值；
2. 判断是否与规则冲突；
3. 输出结论。
```

- **反例**：一段话里塞 10 个要求。
- **要点**：步骤之间有依赖关系时才有意义；独立子任务应拆成多次调用。

## 7. 自检

- **适用**：合规、格式敏感、对外发布的场景。
- **模板**：

```text
输出前检查：
- 是否出现绝对化用语（最强/第一/唯一）？
- 数字与原文是否一致？
- 是否包含联系方式？
若有不满足，先修正再输出。
```

- **反例**：把自检写成"请确保正确"。
- **要点**：检查项必须**可判定**，不能是形容词。

## 8. 拒绝兜底

- **适用**：知识库问答、事实查询（降低幻觉最便宜的手段）。
- **模板**：

```text
只依据资料回答。资料未提及的内容写"未提及"，不要推测。
资料与问题无关时，回答"当前知识库没有找到相关内容"。
```

- **反例**：要求模型"尽量回答"。
- **要点**：给模型一个**合法退路**，比逼它必须回答更可靠；配合代码层阈值拒答。

## 我的实测记录

| 模式 | 用在哪个任务 | 用了之后 | 结论 |
| --- | --- | --- | --- |
| 角色-任务-格式 | Day06 评论分析 v2/v3 | 对比 v1 模糊版，输出从自然段变成可解析 JSON | 角色+格式约束是下限保障 |
| 分隔符隔离 | Day06/07 所有含输入的 prompt | `<review>/<text>` 包住原文，注入样本未污染指令 | 成对、唯一标签即可，不必复杂 |
| 结构化输出 | Day06 三版实验 | 字段+类型+示例，下游直接 json.loads | 必须配合 Pydantic 校验与重试 |
| 先分析后结论 | Day06 v3 情感分析 | analysis 字段强制引用原文，错误率下降 | 思考做成字段，可审计可丢弃 |
| 少样本 | 暂未实测 | — | 待 M1 抽取模板遇到格式边界时用 |
| 分步拆解 | Day07 to_table 任务 | 先提字段再填表，缺失项填 '-' 符合预期 | 步骤之间有依赖才有意义 |
| 自检 | Day07 tone 改写 | "保留数值/禁用词"清单化，3 条样本 PASS | 检查项必须可判定，不能是形容词 |
| 拒绝兜底 | Day07 客服对话 | "不知道就转人工"，注入 3 种话术均未泄露 system | 给退路比逼回答更可靠 |


举例说明

...

你是游戏社区运营编辑，读者是手游玩家。（模式1：角色-任务-格式）

请把 <text> 中的公告改写成玩家社区口吻。（模式2：分隔符隔离）
<text>
{原文}
</text>

改写要求：
- 人称统一用"你"，每句不超过 20 字
- 可用"冲""稳了"，禁用"尊享""礼遇"

按顺序执行：（模式6：分步拆解）
1. 提取 <text> 中所有数字、日期、金额、专名，原样列入 numbers 字段；
2. 基于 numbers 字段做改写，每个值必须原样出现，禁止换算；
3. 逐条核对 numbers 中每个值是否出现在 rewritten 中，
   缺失则在 retry_notes 中说明。

只输出 JSON，不要 markdown 代码块，不要解释。（模式3：结构化输出）
{
  "numbers": ["3000", "10"],
  "analysis": "为什么改写后仍能保留全部数值的 2 句说明，必须引用原文片段",
  "rewritten": "改写后的文本",
  "retry_notes": ""
}

规则：
- numbers 字段若提取不到任何值，rewritten 输出原文，不要编造内容
  （模式8：拒绝兜底）
- 若 <text> 中没有可改写的内容（如纯标点），全部字段输出 null 并说明原因

...



> Day 07 实测补充：normal_1 客服回复中，模型把知识库的"200 钻石 + 1 张普通招募券"说成了"100 星币 + 3 张高级招募券"——
> system 规则 4（金额原样引用）在没有 RAG 注入知识库时形同虚设。
> 这验证了 Day 07 理论第 3 点：**安全边界不能全寄托在 system 上，真正的权限/事实控制必须在代码层。**
